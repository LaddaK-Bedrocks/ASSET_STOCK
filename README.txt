วิธีเปิดดู
----------
ดับเบิลคลิกไฟล์ index.html เพื่อเปิดในเบราว์เซอร์ (Chrome/Edge) ได้เลย ไม่ต้องติดตั้งอะไรเพิ่ม
ไม่ต้องเชื่อมอินเทอร์เน็ต ไม่ต้องต่อฐานข้อมูล — ข้อมูลทั้งหมดเป็นตัวอย่างสมมติ ฝังอยู่ในไฟล์ data.js
คลิก/กรอกฟอร์มได้จริงเพื่อดู flow แต่รีเฟรชหน้าแล้วข้อมูลจะรีเซ็ตกลับค่าตั้งต้นเสมอ

สิ่งที่ทำในรอบที่ 1 (9.1 / 9.2 / 9.4)
-------------------------------------
1. Shell หลัก (sidebar + top bar) — ดึงสี/font/ระยะจากโค้ดจริงของ PMeX (theme.ts, AppLayout.css)
   ให้เนียนไปกับระบบเดิม พร้อมเมนูกลุ่ม 1.0-8.0 เดิมของ PMeX (ย่อไว้ให้เห็นบริบท) และกลุ่มใหม่
   "9.0 ระบบจัดการคลังทรัพย์สิน" ที่มีเมนูย่อยครบ 11 รายการ
2. หน้า 9.1 ภาพรวม (Dashboard) — การ์ดสรุปสถานะ ปรับเนื้อหาตามบทบาทที่สวมอยู่ + ตารางใกล้ครบกำหนดคืน
3. หน้า 9.2 ทะเบียนทรัพย์สิน (Asset Register) — ตาราง master ทรัพย์สินรวม พร้อม filter (ประเภท/flag/
   สถานะ/ค้นหา) และคลิกแถวเพื่อดูรายละเอียด+ประวัติธุรกรรม (drawer)
4. หน้า 9.4 ขอเบิก (Borrow Request) — ฟอร์มขอเบิกแบบ self-service รองรับ 3 วัตถุประสงค์
   (ยืม / ขายขาด / ใช้งานภายใน — เพิ่มตาม feedback) รายการอุปกรณ์กรองตามวัตถุประสงค์อัตโนมัติ
   ส่งคำขอแล้วไปโผล่ในแท็บ "รายการคำขอที่ส่งแล้ว" — มีตัวอย่างคำขอที่จำลองว่ามาจากหน้า PMeX เดิมด้วย

สิ่งที่เพิ่มในรอบที่ 2 (9.3, 9.5-9.11 — ครบทุกเมนูแล้ว)
-------------------------------------------------------
5. หน้า 9.3 รับของเข้าคลัง — โหมดกรอกทีละชิ้น (ครบ field ตามไฟล์ "Upload Printer" จริง) + โหมด
   นำเข้าแบบชุด (จำลองด้วยปุ่ม "นำเข้าตัวอย่าง 3 รายการ") + ตารางรายการรับเข้าล่าสุด
6. หน้า 9.5 จ่ายอุปกรณ์ — คิวคำขอที่รอจ่ายของ คลิกแล้วระบบ auto-suggest Serial Number ที่ว่างให้
   เลือกเปลี่ยนเองได้ (override) ยืนยันแล้วอุปกรณ์เปลี่ยนสถานะเป็น "เบิกแล้ว" ผูกกับโครงการ/แผนกทันที
7. หน้า 9.6 ต่ออายุการยืม — เลือกรายการที่ยืมอยู่ ต่อวันคืนใหม่ได้ พร้อมตารางประวัติการต่ออายุ
8. หน้า 9.7 รับคืนอุปกรณ์ — เลือกเหตุผล (อุปกรณ์เสีย/หมดสัญญา/อื่นๆ) ถ้าเสียจะเข้าคิวซ่อมอัตโนมัติ
   ถ้าไม่เสียกลับเข้าสต๊อกพร้อมใช้งานทันที
9. หน้า 9.8 คิวพิจารณาซ่อม — IT Support ตัดสินใจ "ซ่อมได้" (กลับเข้าสต๊อก) หรือ "ซ่อมไม่ได้"
   (สร้างคำขอ Write-off ให้อัตโนมัติ)
10. หน้า 9.9 คำขอ/อนุมัติ Write-off — รวมคำขอจากทุกที่มา (ซ่อมไม่ได้/ตรวจนับ/แจ้งสูญหาย/อื่นๆ)
    ปุ่มอนุมัติ/ไม่อนุมัติจะใช้ได้เมื่อสวมบทบาท "ผู้อนุมัติ" เท่านั้น (จำลอง RBAC) + สร้างคำขอเองได้
11. หน้า 9.10 ตรวจนับประจำปี — ปุ่ม Export รายการเป็นไฟล์ CSV ได้จริง + ตารางให้ใส่ผลตรวจนับ
    (พบปกติ/ไม่พบ/ชำรุด) ต่อแถว บันทึกแล้วระบบสร้างคำขอ Write-off (ไม่พบ) หรือส่งเข้าคิวซ่อม (ชำรุด) ให้เอง
12. หน้า 9.11 ตั้งค่า Item Master — ตารางประเภทอุปกรณ์ทั้งหมด เพิ่ม/แก้ไข/ลบได้ ตั้ง track S/N,
    Kit+checklist อุปกรณ์ย่อย, และ Scope การใช้งานได้ครบ

สิ่งที่ปรับปรุงในรอบที่ 3 (ตามผลคุยเรื่อง Data Model — ประเภท/สถานะ/properties อุปกรณ์)
--------------------------------------------------------------------------------------
13. เพิ่มชั้น "หมวดหมู่ (Category)" คั่นกลางเหนือ Item Type — จัดการได้เองในหน้า 9.11
    (เพิ่ม/แก้ไข/ลบ) มี guard กันลบหมวดหมู่ที่ยังมีประเภทอุปกรณ์ผูกอยู่ (ต้องย้ายออกก่อน)
    - หน้า 9.2 ทะเบียนทรัพย์สิน เพิ่ม filter ตามหมวดหมู่ และ drawer รายละเอียดแสดงหมวดหมู่ด้วย
    - หน้า 9.3 รับของเข้าคลัง dropdown เลือกประเภทอุปกรณ์จัดกลุ่มตามหมวดหมู่ (optgroup) ให้หาง่ายขึ้น
    - ฟอร์มเพิ่ม/แก้ไข Item Master ในหน้า 9.11 ต้องเลือกหมวดหมู่ทุกครั้ง
14. แยกสถานะ "ขายแล้ว (SOLD)" ออกจากสถานะ "เบิกแล้ว (BORROWED)" — เดิมทั้งยืมและขายขาดใช้สถานะ
    เดียวกัน ตอนนี้เมื่อจ่ายของสำหรับคำขอที่วัตถุประสงค์เป็น "ขายขาด" ระบบจะตั้งสถานะเป็น "ขายแล้ว"
    ทันที (ไม่มีกำหนดคืน ไม่ต้องติดตาม) ส่วน "ยืม"/"ใช้งานภายใน" ยังคงเป็น "เบิกแล้ว" เหมือนเดิม
    - หน้า 9.10 ตรวจนับประจำปี ไม่รวมทรัพย์สินที่ขายแล้วในรายการต้องตรวจนับ (เหมือนที่ตัดจำหน่ายแล้ว)
    - Dashboard มุมมอง OPERATION เพิ่มการ์ดสรุป "ขายแล้ว (สะสม)"
15. ปิดประเด็น field "อายุการใช้งาน (ปี)" และ "รูปถ่ายอุปกรณ์" (ยืนยัน 1 ต.ค. 2569):
    - "อายุการใช้งาน (ปี)" — **ตัดออกจาก schema ทั้งหมด** (ไม่เคยอยู่ในฟอร์มรับของเข้าคลังของ mockup
      อยู่แล้ว เพราะไม่ใช้คำนวณค่าเสื่อมราคาแล้วตามมติเดิม)
    - "รูปถ่ายอุปกรณ์" — **เก็บเป็น path ไฟล์ใน Shared Folder** (ไม่ใช่ไฟล์ภาพอัปโหลดเข้าระบบจริง) —
      เพิ่มช่องกรอกในฟอร์ม 9.3 รับของเข้าคลัง บันทึกแล้วแสดงในหน้ารายละเอียดทรัพย์สิน (9.2)
    - ถือโอกาสต่อเนื่องเดียวกัน: ฟิลด์ "วันสิ้นสุดรับประกัน" ที่เดิมกรอกได้ในฟอร์ม 9.3 แต่ยังไม่เคยถูก
      บันทึกจริง ตอนนี้บันทึกลงทะเบียนทรัพย์สินแล้ว และหน้ารายละเอียด (9.2) จะโชว์ tag "อยู่ในประกัน"/
      "หมดประกันแล้ว" ให้อัตโนมัติเทียบกับวันที่ปัจจุบัน

สิ่งที่ปรับปรุงในรอบที่ 4 (ตามผลคุยเรื่อง UX หน้า 9.5 จ่ายอุปกรณ์ — 1 ต.ค. 2569)

ปัญหาที่แจ้งมา: ตอนจ่ายอุปกรณ์ เดิมมีแค่ dropdown เลือก Serial Number เฉย ๆ ไม่มีข้อมูลประกอบการ
ตัดสินใจ ผู้จ่ายของต้องย้อนไปเปิดหน้าทะเบียนทรัพย์สิน (9.2) แยกต่างหากเพื่อดูประวัติ/สถานที่ ก่อนจะ

16. เปลี่ยนช่องเลือก Serial Number ในหน้า 9.5 จ่ายอุปกรณ์ จาก dropdown ธรรมดา เป็นตารางให้เลือก
    (radio) พร้อมข้อมูลประกอบในตัว โดยเรียงลำดับแนะนำขึ้นบนสุดอัตโนมัติ:
    - ป้าย "เคยอยู่ไซต์นี้มาก่อน" — เทียบจากประวัติจ่าย/รับคืนจริงของเครื่องนั้น ว่าเคยถูกเบิกไปที่
      ไซต์/ลูกค้าเดียวกับคำขอปัจจุบันหรือไม่
    - ป้าย "📍 ใกล้ไซต์นี้" — เทียบภาคของสถานที่เครื่องอยู่ปัจจุบันกับภาคของไซต์ที่ขอเบิก (heuristic
      ใน mockup นี้เท่านั้น ของจริงควรใช้พิกัด/จังหวัดจริงจากฐานข้อมูล)
    - แถวไหนตรงเงื่อนไขมากกว่าจะถูกเลือก (radio) ให้อัตโนมัติเป็นตัวแนะนำเริ่มต้น แต่ผู้จ่ายของ
      ยังเปลี่ยนเลือกแถวอื่นได้เสมอ (override ได้เหมือนเดิม)
17. เพิ่มกล่องข้อมูล "ใกล้ครบกำหนดคืนจากที่อื่น" (สีเหลือง/ไม่ใช่ตัวเลือกให้กด) แสดงเฉพาะเมื่อมีเครื่อง
    ประเภท/การจัดประเภทตรงกับคำขอ ที่กำลังถูกเบิกอยู่ที่อื่นและใกล้ครบกำหนดคืน (ภายใน 14 วัน) — ใช้
    ชี้เป้าให้ผู้จ่ายของเห็นโอกาส "ส่งต่อ" เครื่องจากไซต์ใกล้เคียงแทนที่จะเปิดเครื่องใหม่จากสต๊อก พร้อม
    ปุ่มลัด "ไปหน้ารับคืนอุปกรณ์ →" ที่ปิดหน้าต่างนี้แล้วพาไปหน้า 9.7 รับคืนอุปกรณ์ทันที
    *** ข้อกำหนดสำคัญ (ตามมติ 1 ต.ค. 2569): กล่องนี้เป็นข้อมูลชี้เป้าเท่านั้น ระบบจะไม่ให้ "ส่งต่อ"
    เครื่องแบบปิดรายการเดิม+เปิดรายการใหม่ในขั้นตอนเดียวโดยข้ามการรับคืนจริง — ต้องทำรายการรับคืน
    (พร้อมตรวจสภาพ) ที่หน้า 9.7 ให้เสร็จก่อนเสมอ แล้วเครื่องจะกลับมาเป็น "พร้อมใช้งาน" ให้เลือกจ่าย
    ในคำขอถัดไปตามปกติ ***

    (โชว์แค่ "รหัส — ประเภท") เป็นตารางเลือก (radio) พร้อมข้อมูลประกอบและช่องค้นหา — **ใช้ UX แนวทาง
    เดียวกับตารางเลือก Serial Number ตอนจ่ายอุปกรณ์ในรอบที่ 4 ทุกประการ** (ตาราง radio เรียงลำดับ
    แนะนำขึ้นบนสุดอัตโนมัติ + ค้นหาได้ + ยังเปลี่ยนเลือกแถวอื่นได้เสมอ) แต่เงื่อนไขการแนะนำคนละแบบให้
    เหมาะกับบริบทการตัดจำหน่าย:

     "ส่งซ่อม" (บันทึกร้าน/vendor, วันที่คาดว่าจะเสร็จ, ค่าใช้จ่ายประเมิน แล้วเปลี่ยนสถานะเป็น "กำลังซ่อม
     (ส่งออกแล้ว)") → รอจนซ่อมเสร็จจริง → "ยืนยันซ่อมเสร็จ" (บันทึกวันที่/ค่าใช้จ่ายจริง แล้วกลับเข้าสต๊อก)
     หรือถ้าซ่อมไม่ได้ก็ยังกดไม่ผ่านจากขั้นนี้ได้เหมือนเดิม (ไปสร้างคำขอ Write-off ให้อัตโนมัติ)

     มาจากที่ไหน — ผิดสำหรับกรณีที่มาจาก "ตรวจนับประจำปี (ไม่พบตัว)" หรือสร้างเองแบบ manual เพราะ

    "กำลังซ่อม" (9.8) ให้ดูออกว่าเป็นชื่อที่พิมพ์เอง ยังไม่อยู่ในรายการมาตรฐาน (เผื่อ OPERATION อยากตาม
    ไปเพิ่มเป็น vendor ทางการภายหลัง)
    *** รายชื่อ vendor จริงมีกี่ราย และต้องเก็บข้อมูลติดต่ออะไรบ้าง (เบอร์โทร/อีเมล/ที่อยู่ ฯลฯ) ยังรอ
    user ตอบ — ดูหัวข้อ "คำถามที่รอ user confirm ใน Round 10" ท้ายไฟล์นี้ ***

ข้อ 3 — สถานะ "กำลังซ่อม": เพิ่มตัวบ่งชี้เกินกำหนด
การตัดสินใจที่ล็อกแล้ว: ใช้ลวดลายป้ายเดียวกับป้าย "เลยกำหนดคืน" ของการยืมที่มีอยู่แล้ว เพื่อความสม่ำเสมอ
ของ UI ไม่สร้างสไตล์ใหม่
47. ช่อง "วันที่คาดว่าจะซ่อมเสร็จ" ในฟอร์ม "ส่งซ่อม" ยังคงเป็นช่องไม่บังคับกรอกเหมือนเดิม แต่ตารางแท็บ
    "กำลังซ่อม" (9.8) ตอนนี้มีคอลัมน์ "ระยะเวลา" เพิ่มเข้ามา ทุกแถวจะแสดงข้อความ "อยู่ระหว่างซ่อม X วัน"
    เสมอ (นับจากวันที่ส่งซ่อม) ถ้าตอนส่งซ่อมมีการกรอกวันที่คาดว่าจะเสร็จไว้ แล้วตอนนี้เลยวันนั้นมาแล้ว จะขึ้น
    ป้ายแดง "⏰ เกินกำหนดซ่อม (เกิน X วัน)" ต่อท้าย — ถ้าไม่ได้กรอกวันคาดเสร็จไว้เลย ระบบจะใช้ค่าตั้งต้น
    30 วันนับจากวันส่งซ่อมแทนเป็นเส้นแบ่งว่าเกินกำหนดหรือยัง แล้วขึ้นป้ายแดงแบบเดียวกันเมื่อเกิน — ป้ายแดงนี้
    ใช้สไตล์ tag-red เดียวกับป้าย "⏰ เลยกำหนดคืนแล้ว" ที่มีอยู่แล้วในตัวเลือกทรัพย์สินตอนจ่ายของ/Write-off
    ไม่ได้สร้างสีหรือสไตล์ใหม่ขึ้นมา
48. เพิ่ม checkbox ตัวกรอง "เฉพาะที่เกินกำหนด" เหนือตารางแท็บ "กำลังซ่อม" — ติ๊กแล้วตารางจะกรองเหลือ
    เฉพาะแถวที่เกินกำหนดซ่อม ส่วนเลขจำนวนรายการที่แสดงบนชื่อแท็บยังนับรวมทุกสถานะเหมือนเดิม ไม่ใช่เลข
    ที่ถูกกรองด้วย checkbox นี้
49. เพิ่มข้อมูลตัวอย่างครบ 4 กรณีในแท็บ "กำลังซ่อม": (ก) กรอกวันคาดเสร็จไว้และยังไม่เกินกำหนด, (ข) กรอก
    วันคาดเสร็จไว้แล้วเลยกำหนดมาแล้ว (เกิน 4 วัน), (ค) ไม่ได้กรอกวันคาดเสร็จและยังไม่ครบ 30 วัน (ตัวอย่าง
    นี้ส่งซ่อมผ่านช่อง "อื่น ๆ" ด้วย เพื่อให้เห็นป้าย "พิมพ์เอง" พร้อมกันในแถวเดียว), (ง) ไม่ได้กรอกวันคาดเสร็จ
    และเกิน 30 วันไปแล้ว (เกิน 32 วัน)
    *** ตัวเลข 30 วัน เป็นค่าตั้งต้นที่ใส่ไว้ก่อนในโค้ด (REPAIR_OVERDUE_DEFAULT_DAYS) ยังรอ user confirm
    ว่าเหมาะสมหรือไม่ — ดูหัวข้อ "คำถามที่รอ user confirm ใน Round 10" ท้ายไฟล์นี้ ***

สิ่งที่ไม่ได้ทำเพิ่มในรอบนี้ (ตามคำสั่ง user ว่าไม่ให้เพิ่ม feature นอกเหนือจาก 3 ข้อข้างบน):
- ไม่ได้ทำหน้าจัดการรายชื่อ vendor (เพิ่ม/แก้ไข/ลบ) — รายชื่อยัง hard-code ไว้ในโค้ด
- ไม่ได้ทำ flow เปลี่ยน vendor หรือยกเลิกการส่งซ่อมระหว่างทาง (ยังเป็นข้อจำกัดเดิมจาก Round 9)
- ไม่ได้ปรับสี/ป้าย/layout ตารางใด ๆ ที่มีอยู่แล้ว (ตามที่ user ขอให้รักษาสไตล์เดิมทั้งหมด)

ข้อเสนอแนะเพิ่มเติม (ไม่ได้ลงมือทำ แค่เขียนทิ้งไว้ให้พิจารณาในรอบถัดไป):
- อาจพิจารณาแจ้งเตือนผู้ขอเบิกล่วงหน้า (เช่น แจ้งก่อนร่างหมดอายุ 1-2 วัน) แทนที่จะให้ไปเห็นเองตอนเข้า
  หน้าเว็บ — รอบนี้ยังไม่มีระบบแจ้งเตือนแบบ push/email ใน mockup
- อาจพิจารณาให้ OPERATION เห็นรายการร่างที่ใกล้หมดอายุ/หมดอายุแล้วแยกต่างหาก เผื่อต้องการติดตาม
  ผู้ขอเบิกที่ปล่อยร่างหมดอายุบ่อย ๆ
- อาจพิจารณาเพิ่มเหตุผลยอดนิยมเป็นตัวเลือกสำเร็จรูปในช่อง "เหตุผลที่ยกเลิกร่าง" แทนพิมพ์เองล้วน
  เพื่อเก็บข้อมูลให้วิเคราะห์ง่ายขึ้นภายหลัง

คำถามที่รอ user confirm ใน Round 10
------------------------------------
1. ร่างคำขอเบิกทดแทนอัตโนมัติควรหมดอายุใน "กี่วัน" นับจากวันที่ระบบสร้างให้ — ตอนนี้ mockup ใส่ไว้ที่
   14 วันเป็นตัวอย่างเท่านั้น
2. สถานะ "กำลังซ่อม" ควรถือว่า "เกินกำหนด" เมื่อไม่มีวันคาดว่าจะเสร็จระบุไว้ — ตอนนี้ mockup ใส่ไว้ที่
   30 วันนับจากวันส่งซ่อมเป็นตัวอย่างเท่านั้น
3. รายชื่อร้าน/vendor ที่ใช้ส่งซ่อมจริงมีกี่ราย ชื่ออะไรบ้าง และต้องเก็บข้อมูลติดต่ออะไรบ้าง (เบอร์โทร
   อีเมล ที่อยู่ ผู้ติดต่อ ฯลฯ) เพื่อนำไปใส่เป็นรายชื่อจริงแทนตัวอย่าง 5 รายที่ใส่ไว้ก่อน

ข้อจำกัดที่ทราบแล้ว ยังไม่ได้ทำในรอบนี้ (ตามที่คุยกับ user แล้วว่ายังไม่ต้อง auto-route):
- เมื่อแจ้งปัญหาแล้ว ระบบยังไม่ส่งต่อเคสไปที่ไหนอัตโนมัติ (ไม่เข้าคิวซ่อม ไม่สร้าง Write-off) — เป็นแค่
  flag ให้ OPERATION เห็นแล้วไปจัดการเอง ตามมติที่คุยกันไว้
- การยืนยันรับของเป็นแบบ "ทั้งคำขอ" ต่อการกดครั้งเดียว (เช็กทีละแถวแล้วสรุปผลรวมครั้งเดียว) ยังไม่มี
  flow แยกย่อยกรณี "รับบางส่วน" (เช่น อุปกรณ์ 1 ใน 2 ชิ้นยังไม่ถึงมือ) ซึ่งเป็น edge case ที่ยังไม่ได้
  คุยรายละเอียด
- [ปิดแล้วใน Round 10 — ดูข้อ 42-44] คำขอเบิกทดแทนอัตโนมัติ (ข้อ 37) สร้างเป็น "ร่าง" รอ OPERATION
  จ่ายของต่อเองเท่านั้น ยังไม่มี flow ยกเลิกคำขอทดแทนนี้ถ้าสุดท้ายไม่ต้องการแล้ว
- ขั้นตอน "ส่งซ่อม" ยังไม่รองรับกรณีส่งซ่อมแล้วต้องเปลี่ยนร้าน/vendor ระหว่างทาง หรือยกเลิกการส่งซ่อม
  กลับมาเป็น "รอพิจารณาซ่อม" เหมือนเดิม (การเพิ่ม dropdown เลือก vendor ใน Round 10 เป็นแค่เปลี่ยนวิธี
  กรอกชื่อ vendor ตอนส่งซ่อมครั้งแรก ยังไม่รวมเรื่องเปลี่ยน/ยกเลิกระหว่างทาง)

## Round 11 — เพิ่ม filter/ค้นหาในตาราง "รายการคำขอที่ส่งแล้ว"

**คำถามของ user ก่อนขอ Round 11 (verbatim):** "รายการคำขอที่ส่งแล้ว => คือรายการของที่เบิกไปแล้ว
ทั้งหมดใช่มั้ย ถ้าเป็นผู้เบิก จะเห็นเฉพาะที่ตัวเองเบิกใช่มั้ย (ตอบ ใช่) อยากให้เพิ่ม filter ให้ด้วย
เช่น ค้นจาก โครงการ จังหวัด หรือ ชื่อ และอื่นๆตามเหมาะสม"

*** ข้อค้นพบสำคัญที่ต้องแจ้ง user ก่อน (ตรวจโค้ดจริงแล้วพบว่าไม่ตรงกับที่ user เข้าใจ): ตอนนี้ตาราง
"รายการคำขอที่ส่งแล้ว" (9.4) ดึงจาก `borrowRequests` ทั้งก้อนเสมอ (`const pending = borrowRequests`)
ไม่มีการกรองตาม "ตัวตนผู้ขอเบิก" เลย — ไม่ว่าจะสวมบทบาท Asset Holder แล้วเปิดดูกี่ครั้ง จะเห็นคำขอ
ตัวอย่างทั้งหมดในระบบเหมือนกันทุกครั้ง เพราะ mockup นี้จำลองแค่ "สวมบทบาท" (role: Asset Holder/
OPERATION/IT Support/ผู้อนุมัติ) ไม่ได้จำลอง "login เป็นใครคนใดคนหนึ่ง" — จึงไม่มีแนวคิด "ตัวฉันเอง"
ให้กรองจริง ๆ ในระบบนี้ ต่างจากที่ user เข้าใจว่า "ถ้าเป็นผู้เบิก จะเห็นเฉพาะที่ตัวเองเบิก" ซึ่งยังไม่เป็น
จริงในโค้ดตอนนี้ — ยังไม่ได้แก้ส่วนนี้ในรอบนี้ (ดูคำถามท้ายหัวข้อนี้) แต่เพิ่ม filter/ค้นหาตามที่ขอให้
ก่อนแล้ว เพื่อให้หาคำขอที่ต้องการเจอง่ายขึ้นในระหว่างที่ตารางยังโชว์ทุกคำขอปนกันอยู่ ***

**สิ่งที่ implement ลง mockup:**

50. เพิ่มแถบตัวกรองเหนือตาราง "รายการคำขอที่ส่งแล้ว" (9.4) 3 ส่วน: (ก) ช่องค้นหาแบบ live filter
    (พิมพ์แล้วกรองทันที รูปแบบเดียวกับช่องค้นหาในหน้าอื่น ๆ) ค้นหาครอบคลุม เลขคำขอ, ชื่อผู้ขอ, ทีม,
    โครงการ/ลูกค้า, และชื่อรายการอุปกรณ์ในคำขอนั้น — (ข) dropdown กรองตาม "วัตถุประสงค์" (ยืม/ขายขาด/
    ใช้งานภายใน) — (ค) dropdown กรองตาม "สถานะ" (รอจ่ายของ/เบิกแล้ว/หมดอายุ/ยกเลิกแล้ว — 2 สถานะหลัง
    คือสถานะร่างทดแทนจาก Round 10) — ทั้ง 3 ตัวกรองทำงานร่วมกันได้ (AND) และมีข้อความ "แสดง X จาก Y
    รายการ" โชว์เฉพาะตอนมีการกรองอยู่ ส่วนเลขนับในชื่อแท็บ (เช่น "รายการคำขอที่ส่งแล้ว (11)") ยังคงนับ
    รวมคำขอทั้งหมดเหมือนเดิมเสมอ ไม่ใช่เลขที่ถูกกรอง (แนวทางเดียวกับตัวกรอง "เฉพาะที่เกินกำหนด" ของ
    Round 10 ข้อ 3) — ถ้ากรองแล้วไม่พบคำขอที่ตรงเงื่อนไข ตารางแสดงข้อความ "ไม่พบคำขอที่ตรงกับเงื่อนไข
    ค้นหา" แทนแถวว่างเปล่า
    *** หมายเหตุเรื่อง "จังหวัด": ข้อมูลคำขอในตอนนี้ยังไม่มีฟิลด์ "จังหวัด" แยกต่างหาก — ช่อง
    "โครงการ/ลูกค้า" เป็น free-text ที่บางครั้งมีชื่ออำเภอ/ตำบล/เกาะปนอยู่ (เช่น "ขอนแก่น", "เกาะสมุย")
    ซึ่งพิมพ์ค้นหาแล้วจะเจอได้ถ้าคำที่พิมพ์ตรงกับข้อความนั้นเป๊ะ ๆ แต่ไม่ใช่ตัวกรองจังหวัดที่แม่นยำจริง
    (เช่น ค้นหา "สุราษฎร์ธานี" จะไม่เจอคำขอที่โครงการเขียนไว้แค่ "เกาะสมุย") — ถ้าต้องการกรองจังหวัดแม่นยำ
    จริง ต้องเพิ่มฟิลด์ "จังหวัด" แยกต่างหากในข้อมูลคำขอก่อน (ดูคำถามท้ายหัวข้อนี้) ***

**ข้อจำกัดที่ยังเหลือหลัง Round 11 / คำถามที่รอ user ตอบ:**
- ตารางนี้ยังแสดงคำขอ "ทั้งหมด" ให้ทุกคนที่สวมบทบาท Asset Holder เห็นเหมือนกัน ไม่ได้กรองเฉพาะคำขอของ
  "ตัวเอง" ตามที่ user เข้าใจไว้ — อยากให้ Claude เพิ่มการจำลอง "login เป็นใครคนหนึ่ง" (เช่น เลือกชื่อ
  ผู้ใช้ในมุมมอง Asset Holder แล้วตารางกรองเฉพาะคำขอที่ "ผู้ขอ" ตรงกับชื่อนั้น) ในรอบถัดไปหรือไม่ หรือ
  มองว่าสำหรับ mockup ขั้นนี้ให้ OPERATION/ผู้ขอเบิกทุกคนเห็นภาพรวมเดียวกันไปก่อนก็พอ (ของจริงเมื่อต่อ
  ระบบ login จริงแล้วค่อยกรองตาม user ที่ login)
- ไม่มีฟิลด์ "จังหวัด" แยกต่างหากในข้อมูลคำขอ — อยากให้เพิ่มฟิลด์นี้เข้าไปในฟอร์ม "ขอเบิก" (9.4) เพื่อ
  กรองได้แม่นยำขึ้นหรือไม่ หรือใช้ช่องค้นหาแบบ free-text ที่ทำไว้รอบนี้ก็เพียงพอสำหรับขั้น mockup

เครื่องมือช่วยดูใน mockup (ไม่ใช่ของจริง)
------------------------------------------
